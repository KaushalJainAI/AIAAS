# Agent observability

What an agent did, what it was thinking, and what it was configured as — a
run is a **loop of turns**, not a pipeline of steps. Each turn the model
reasons, issues zero or more tool calls *together*, gets every result back
into the same model, and reasons again.

```
SubAgentRevision ──┐
                   ├── ExecutionLog ─── AgentTurn ─── AgentStep
   the config          one run          one model      one tool
                                        call           call
                                                         │
                                                         └── delegated runs
                                                             (ExecutionLog.parent_step)
```

| Table | One row per | Answers |
|---|---|---|
| `SubAgentRevision` | configuration change | "what was it when it did that?" |
| `ExecutionLog` | run | "did it work, what did it cost, who asked?" |
| `AgentTurn` | model call | "what was it thinking, and what did it decide?" |
| `AgentStep` | tool call | "what did it actually do, and did it work?" |

Calls sharing a turn return to the *next* turn, never to each other — the
difference between drawing an agent as the loop it is and a pipeline it never
was.

## The turn hook

`TurnContext.on_model_turn` (`chat/turn/agent.py`) mirrors `on_tool_result`.
Chat turns pass `None` and behave exactly as before — the same contract
`tool_source` / `tool_dispatch` / `sensitive_tools` already use.

It receives `completion.thinking`, **never** the accumulated `thinking` state;
the running total would grow quadratically and attribute turn 1's thoughts to
turn 7. Neither observer may raise — a run that did the work must not be
reported as failed because something was watching it.

## Steps open before the tool runs

`AgentRunStream._tool_started` writes the `AgentStep` row with
`status='running'` *before* dispatch, and `on_tool_result` closes that same
row. Two reasons: delegation happens during dispatch (a worker records the
step that asked for it, so the row must exist first), and a long call such as
`deep_research` must be visible in the persisted trace while it runs, not
after.

## Delegation points at a step, not at a run

```python
ExecutionLog.parent_step -> AgentStep
```

One FK answers both halves of "who asked for this, and why":
`parent_step.execution` is the orchestrating run; `parent_step.turn.reasoning`
is what it was thinking when it delegated. A run-to-run link would lose the
second. `delegation_task` is stored because a worker's goal is generated by
the parent model at run time and exists nowhere else once the parent's
transcript is gone.

`caller` is stored separately from `trigger_type`. `trigger_type` says *how*
a run was invoked; `caller` says *what* invoked it
(`api | chat | orchestrator | trigger | eval | mission`). Eval runs are
`caller='eval'` and are excluded from user-facing stats and the run list.
Both a chat delegation and a direct API call arrive as `trigger_type='api'`;
telling them apart is the difference between "the user asked for this" and
"an agent decided to spend the user's credits on it".

## Configuration history

`SubAgentRevision` snapshots `AgentSerializer.to_config(agent)` — the same
flat `AgentConfig` dict the builder speaks. A second mapping would drift
from the UI.

`ExecutionLog.revision` pins each run to the configuration it executed under,
taken at run *open* time, so an agent edited mid-run does not retroactively
change what its running executions claim to have used.

Rules in `logs/revisions.py`:

- **A revision is only written when something changed.** `record()` returns
  `None` on a no-op; callers must not treat that as failure.
- **An agent predating revision tracking gets one minted lazily** on its next
  run (`revisions.current`, `source='backfill'`), so every run has something
  to point at.

The summary names what moved — `"model, autonomy, tools"` — rather than
counting it. `"3 fields changed"` never tells you whether to look.

## Bounds

No pruning; every field is capped instead (`workflow_backend/thresholds.py`):

| Constant | Bounds |
|---|---|
| `TURN_REASONING_CHAR_LIMIT` (8k) | one turn's reasoning |
| `TURN_CONTENT_CHAR_LIMIT` (4k) | one turn's visible output |
| `REVISION_VALUE_CHAR_LIMIT` (4k) | each side of one field's diff |
| `stream.MAX_PAYLOAD_CHARS` (4k) | a step's args and result |
| `EXECUTION_NODE_LOG_LIMIT` (500) | steps returned by the detail endpoint |
| `EXECUTION_TURN_LIMIT` (200) | turns returned by the detail endpoint |
| `REVISION_TIMELINE_LIMIT` (200) | revisions returned by the timeline endpoint |

Anything trimmed is **marked** — `reasoning_truncated`, `content_truncated`,
`steps_truncated`, `turns_truncated`, and the timeline's `truncated`. A cut
thought and a genuinely brief one must not look alike.

A step whose turn row is missing (a backfilled run, or a failed write) is
returned under `unattributed_steps` rather than dropped. The agent still did
the work.
